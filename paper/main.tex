\begin{abstract}
Digital twins promise operational insight for warehouses and distribution
centres, but building one still depends on laser scans, CAD models and
simulation specialists, which puts them out of reach for most small operators
and almost all non-profits. We present \emph{Auto-Twin}, an open pipeline that
turns an ordinary walkthrough video into a live spatial digital twin in three
steps. First, a generative world model reconstructs the space as 3D Gaussian
splats from a handful of video frames and plausibly extrapolates the parts the
camera never saw. Second, the twin is bound to existing operational data
(cold-chain sensors, forklifts, inventory systems) through a serverless AWS
layer with no standing cost. Third, NVIDIA Omniverse renders the twin with live
data, while a zero-install browser viewer and Blender serve as alternatives.
OpenUSD, and its native \code{ParticleField3DGaussianSplat} schema, is the open
contract that connects the three steps, so each can be replaced without
touching the others. We demonstrate the pipeline on a food bank warehouse
inspired by the Central Texas Food Bank, reconstructed from a public news
walkthrough, and report \TBD{end-to-end time}, \TBD{world-model cost in
credits and USD} and \TBD{monthly cloud cost}. Code is available at
\url{https://github.com/pikulsomesh/foodbank-spatial-twin}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A digital twin is a virtual representation of a physical asset that stays
synchronised with it through data~\citep{grieves2017digital,kritzinger2018digital}.
In industry, twins are used to plan layouts, monitor equipment and rehearse
changes before they are made on the floor~\citep{tao2019digital,fuller2020digital}.
The geometry of a facility twin is usually the expensive part: it comes from
terrestrial laser scanning, photogrammetry campaigns or hand-built CAD, and
it then has to be imported into a simulation tool by specialists. That cost is
tolerable for an automotive plant. It is prohibitive for a regional food bank,
which runs warehouse-scale cold-chain logistics on a non-profit budget.

Two developments change that cost structure. Neural scene representations,
and 3D Gaussian Splatting in particular~\citep{kerbl20233d}, produce
photorealistic, real-time renderable scenes from images. Generative world
models~\citep{ha2018world,brooks2024video,worldlabs_marble} go further: from
a few views they produce a coherent, explorable 3D world, filling in regions the
input never covered. In parallel, OpenUSD~\citep{openusd} has become an open,
vendor-neutral scene description, and its 26.03 release added a native schema
for Gaussian splats~\citep{aousd2603,usd_gsplat_schema}. A splat reconstruction
is therefore no longer a viewer-specific file; it can be a first-class asset in
the same stage as sensors, equipment and annotations.

This paper asks whether these pieces can be composed into a twin that a small
team can build from a phone video, quickly and at very low cost. Our
answer is a three-step pipeline (Figure~\ref{fig:overview}):

\begin{enumerate}[leftmargin=*,itemsep=2pt]
  \item \textbf{Video to digital twin with world models.} Blur-aware frame
        extraction feeds a world model that returns a Gaussian-splat world,
        which is converted to an OpenUSD \code{ParticleField3DGaussianSplat}
        stage in metric, Y-up coordinates (Section~\ref{sec:step1}).
  \item \textbf{Connect existing data systems in AWS.} A serverless API
        exposes operational data in the twin's coordinate frame through a
        small, versioned JSON contract. The reference implementation simulates
        cold-chain telemetry; the contract is designed so that AWS IoT Core,
        a time-series store or an existing warehouse management system can
        replace the simulator without changing any renderer (Section~\ref{sec:step2}).
  \item \textbf{NVIDIA Omniverse as the visualisation layer.} Omniverse
        renders the USD twin with live data bound to prims. A browser viewer
        and Blender read the same USD and the same JSON, so the renderer is a
        deployment choice rather than an architectural one (Section~\ref{sec:step3}).
\end{enumerate}

\paragraph{Contributions.}
\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item An end-to-end, open-source pipeline from walkthrough video to an
        Omniverse-ready OpenUSD Gaussian-splat twin, including the coordinate
        and packaging corrections needed to make world-model output a valid,
        metric USD asset (Section~\ref{sec:step1}).
  \item An architecture in which OpenUSD and a small telemetry contract are
        the only interfaces between reconstruction, data and rendering, with
        a serverless AWS reference backend that has no standing cost
        (Sections~\ref{sec:overview}--\ref{sec:step2}).
  \item Cost controls for paid generative APIs (draft-only policy,
        resume-never-resubmit, a lifetime credit ledger) that make
        world-model reconstruction safe to run in CI (Section~\ref{sec:cost}).
  \item A Tech-for-Good case study: a food bank warehouse twin built from a
        public news walkthrough, with an honest account of what the world model
        observed and what it invented (Section~\ref{sec:case}).
\end{itemize}

\section{Background and related work}
\label{sec:related}

\paragraph{Digital twins.}
The concept is usually traced to product lifecycle management~\citep{grieves2017digital}.
Surveys distinguish digital models, shadows and twins by the direction and
automation of data flow~\citep{kritzinger2018digital} and identify
geometry acquisition, data integration and interoperability as the recurring
barriers~\citep{tao2019digital,fuller2020digital}. Our work addresses the first
and third barrier directly and keeps the second deliberately thin.

\paragraph{Scene reconstruction from images.}
Classical pipelines recover camera poses with structure-from-motion~\citep{schoenberger2016sfm}
and then densify. Neural radiance fields~\citep{mildenhall2020nerf} improved
view synthesis but are slow to render. 3D Gaussian Splatting~\citep{kerbl20233d}
represents a scene as anisotropic Gaussians with view-dependent colour and
renders in real time, which is what makes it practical for an interactive
twin. Learned multi-view geometry such as DUSt3R~\citep{wang2024dust3r}
reduces the number and quality of views needed. All of these reconstruct only
what was observed.

\paragraph{Generative world models.}
World models learn a predictive model of an environment~\citep{ha2018world};
recent video and 3D generators produce consistent explorable
scenes~\citep{brooks2024video}. World Labs' Marble~\citep{worldlabs_marble}
generates Gaussian-splat worlds from text, images or video and exposes them
through an API. For a twin, generation has a double edge: it completes
occluded and unfilmed regions, which makes a sparse walkthrough usable, but it
also invents geometry. Section~\ref{sec:discussion} discusses how we label the
difference.

\paragraph{OpenUSD and Omniverse.}
Universal Scene Description, originally from Pixar and now developed under the
Alliance for OpenUSD, is a layered scene description with composition, schemas
and a plugin architecture~\citep{openusd}. Version 26.03 introduced the
\code{ParticleField3DGaussianSplat} schema family~\citep{aousd2603,usd_gsplat_schema}.
NVIDIA Omniverse~\citep{omniverse} is a USD-native platform for real-time RTX
rendering and simulation. Its licensing is mixed: some components are released
as open source, while the Kit SDK is distributed under NVIDIA's own license
terms~\citep{kit_app_template}. \TBD{confirm Kit runtime license text and cite
the license file before submission}.

\section{Step 1: from video to a world-model twin}
\label{sec:step1}

\subsection{Frame extraction}
A walkthrough video is dense and redundant, while world-model APIs accept
only a few images (Marble's multi-image mode accepts at most eight with
reconstruction enabled~\citep{worldlabs_marble}). The ingest stage samples a
window of the video and, for every interval of $N$ seconds, scores several
candidate frames with ffmpeg's blur detector and keeps the sharpest; interlaced
frames are deinterlaced only when flagged. A hard cap of 40 frames bounds
storage and upload. Burned-in broadcast graphics can be cropped, and all kept
frames share one resolution, which reconstruction requires.

From the 40-frame pool, an automatic picker splits the sequence into equal
segments and keeps the frame with the highest variance of the Laplacian in
each. On interview-style footage this fails: Laplacian sharpness rewards
in-focus faces, and on our case-study video it selected six near-identical
shots of the presenters. We therefore chose the eight inputs by hand for
viewpoint spread and absence of people (Section~\ref{sec:case}).
\TBD{replace with a person-aware picker (detector penalty plus pose diversity)
and report its selection against the hand-picked set, or keep hand selection
and say so}.

\subsection{World-model reconstruction}
\label{sec:worldmodel}
The selected frames are uploaded and a world is generated. Two routes on the
World Labs platform are implemented or under evaluation:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
  \item \textbf{Direct world generation.} A multi-image request to Marble
        returns a Gaussian-splat world in SPZ format~\citep{spz} together with
        a metric scale factor and a ground-plane offset~\citep{worldlabs_spz}.
        The draft model is used throughout.
  \item \textbf{Posed RGB-D then local fusion.} The Marble~2 developer API
        estimates camera poses and depth for the input frames and generates
        additional posed RGB-D views of the scene; splats are then fitted
        locally from those views.
\end{enumerate}
\TBD{state which route produced the reported twin, its exact API tasks and
model names, and the credits it consumed}. In both routes the world model
completes regions outside the filmed path. We treat this as a feature for a
planning twin and a risk for an operational one (Section~\ref{sec:discussion}).

\subsection{SPZ to OpenUSD}
\label{sec:usd}
The splat world is converted with \code{usd-convert-gsplat}~\citep{usdconvertgsplat}
into a \code{ParticleField3DGaussianSplat} prim. Four details turned out to
matter.

\paragraph{Coordinate frame.} World Labs SPZ files use an OpenCV-style camera
frame (Y down) in arbitrary units~\citep{worldlabs_spz}. Leaving the splat
payload untouched, we place it under a parent transform
\begin{equation}
  M = R_x(180^\circ)\; T(0, -o, 0)\; S(s),
\end{equation}
where $s$ is the world's metric scale factor and $o$ its ground-plane offset,
and set the stage to Y-up with \code{metersPerUnit}$\,=1$. With synthetic
input the ground lands at exactly $y=0$; metric units are what let telemetry
positions be expressed in metres.

\paragraph{Untyped reference prim.} A typed \code{Xform} that references the
splat would override the referenced prim's schema type and hide the
splat. The pipeline therefore authors \code{/World/FoodBank} as the
transforming \code{Xform} and \code{/World/FoodBank/Splat} as an untyped prim
carrying the reference, and verifies after packaging that a prim of type
\code{ParticleField3DGaussianSplat} with positions exists.

\paragraph{Packaging.} Converter version 0.1.15 writes a direct \code{.usdz}
as an ASCII layer zipped without the 64-byte alignment that the USDZ
specification requires. We convert to binary \code{.usdc} and package with
OpenUSD's \code{UsdUtils.CreateNewUsdzPackage}.

\paragraph{Size.} SPZ quantises positions to 24-bit fixed point and most
attributes to 8 bits, then compresses; USD stores float32 arrays and USDZ is
uncompressed by specification. In a synthetic test with 20{,}000 splats at
spherical-harmonic degree~1, the SPZ was 262\,KB and the USDZ 2.0\,MB
($7.7\times$). \TBD{report SPZ and USDZ sizes and splat counts for the case-study
twin}. The schema defines half-precision attributes that would roughly halve
this; the converter does not yet write them.

\subsection{Cost controls for paid generation}
\label{sec:cost}
Generative reconstruction is the only paid, non-idempotent step, so it is
guarded in code rather than by convention: only the draft model is allowed
unless explicitly overridden, and the model is checked again in the payload
and in the returned world; each process makes at most one billable call; the
operation id is persisted the moment a job is accepted, so a crash resumes
polling instead of paying again; a finished world is reused unless a new one
is forced; a lifetime ledger refuses any run that would exceed the budget; a
live balance check requires a reserve; and the billable request is retried
only on HTTP~429, which the API defines as not accepted, never on timeouts or
server errors. These guards were exercised against a local mock of the API
(retry on 429, a 503 during polling, resume in flight with exactly one
generation across three runs, reuse, refusal of non-draft models, ledger
accounting). \TBD{report real credits spent per twin and per experiment}.

\section{Step 2: connecting existing data systems in AWS}
\label{sec:step2}

The data step exposes operational state, positioned in the twin's frame, at
minimum cost. The reference backend is one AWS SAM template~\citep{awssam}:
\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item an S3 bucket serving the twin assets and the web viewer;
  \item a Python~3.12 Lambda function on arm64 with 128\,MB of memory and a
        3\,s timeout, behind an HTTP API with \code{GET /telemetry} and
        \code{GET /health}, throttled to 5 requests per second (burst 10) as a
        cost ceiling;
  \item a log group with seven-day retention.
\end{itemize}
There is no VPC, NAT gateway, database or provisioned capacity, so an idle
twin costs nothing beyond storage. \TBD{measured monthly cost at demo traffic,
from the AWS bill}.

\paragraph{Simulated telemetry.} The reference function is stateless and
deterministic: every value is a function of the wall clock, so two clients in
the same second see the same state without shared storage. It models three
cold-chain zones (freezer, cooler, dry storage) with setpoints of
$-18^\circ$C, $3^\circ$C and $21^\circ$C, slow drift, jitter, door events and
alarm bands, plus a forklift following a closed path between the dock and the
storage aisles. Responses are cacheable for two seconds so that polling
viewers are absorbed by caches. Every payload carries \code{simulated: true}.

\paragraph{From simulation to real systems.} The simulator is a placeholder
for connectors to systems a food bank already runs. Because renderers depend
only on the contract in Table~\ref{tab:contracts}, a connector replaces the
function body and nothing else. The cheapest honest first step is AWS IoT
Core~\citep{awsiotcore} receiving MQTT messages from temperature loggers,
with the latest value per zone kept in a key-value store and served by the same
endpoint; time-series history and inventory data from a warehouse management
system follow the same pattern. \TBD{describe the first real connector that is
actually deployed, or state that the evaluation uses simulated data only}.

\paragraph{Spatial binding.} Each zone and asset carries an anchor in metres in
the twin frame. Anchors are calibrated once against the reconstructed stage.

\paragraph{Why a food bank.} Food banks operate warehouse-scale logistics,

small technical teams. A twin that can be built from a phone video and run
for near zero cost is the kind of tool that is usually out of their reach.

an exact replica, and the world model adds plausible operational areas that
the source video does not show. \TBD{obtain and acknowledge permission from

\paragraph{Fidelity protocol.} Frames from the extraction window that were not
given to the world model are held out. Their camera poses are estimated
against the reconstruction and the twin is rendered from those poses; we report
PSNR, SSIM and LPIPS on the held-out set. Because the world model is allowed to
invent unseen content, fidelity is meaningful only in observed regions; it is
not a measure of the extrapolated areas. \TBD{confirm protocol and pose

\section{Discussion and limitations}
\label{sec:discussion}

\paragraph{Generated is not measured.} A world model completes what the camera
did not see. That is useful for a planning or communication twin and unsafe if
someone reads a generated aisle as the real one. Generated regions should be
marked in the stage, for example with a USD attribute on splats or a separate
layer, so renderers can show them differently. \TBD{whether this was
implemented}.

\paragraph{Metric accuracy.} Scale comes from the world model's metric
estimate, not from a survey. Absolute dimensions should be checked against at
least one known measurement before the twin is used for layout decisions.

\paragraph{Input quality.} People, motion blur, reflective steel and
repetitive racking are hard cases. Masking people before reconstruction would
help; the Marble~2 API exposes masked inputs, which we have not yet evaluated.

\paragraph{Privacy and permission.} Walkthrough videos capture staff,
volunteers and clients. Faces should be removed or the space filmed when empty,
and the facility's permission obtained before a reconstruction is published.

\paragraph{Licensing.} OpenUSD is open source and Blender is GPL; Omniverse
combines open components with NVIDIA-licensed runtime pieces. The architecture
does not depend on any single renderer, so an organisation can choose by
hardware, cost and license posture.

\section{Conclusion}
A spatial digital twin does not have to start with a laser scanner. A short
walkthrough video, a generative world model and OpenUSD's native splat schema
produce a metric twin that Omniverse can render, and a serverless data layer
connects it to the systems an operator already has for almost no standing
cost. Keeping OpenUSD and a small JSON contract as the only interfaces makes
each step replaceable as world models, data platforms and renderers improve.
